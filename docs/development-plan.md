# MallAgent 后端开发计划

> 版本：v2.1（2026-11-02）——阶段 0–4 已通过验收；阶段 6/7 MVP 简化版（订单 + 模拟支付）已实现；优惠券、物流、售后未开始
> 范围：Java 后端 MVP + Vue 3 用户端前端 MVP（`frontend/`）。Python AI Agent 不在本计划内。
> 配套规范：`CLAUDE.md`
> 工程形态：当前为**单 Maven 模块**（根 `pom.xml`，`artifactId=mallagent`，`packaging=jar`）。文中历史阶段出现的 `mallagent-module-*` 仅表示当时的包边界名称，旧多模块目录已不存在。

## 0. MVP 最小可行方案（速览）

> 本节是执行摘要；详细交付物与验收标准见第 3、4 节。

**目标**：用最小范围跑通“浏览 → 加购 → 下单 → 支付 → 发货 → 收货 → 退款”的完整交易闭环。

**最小范围**：阶段 0–9，共 10 个阶段。

| 环节 | 阶段 | 最小能力 |
| --- | --- | --- |
| 浏览 | 0–2 | 工程基座、登录鉴权、商品分类/SPU/SKU 查询 |
| 加购 | 3 | 购物车增删改查、选中、服务端金额汇总 |
| 下单 | 4–6 | 库存锁定/扣减/释放、优惠券锁定/核销、订单状态机 |
| 支付 | 7 | 模拟支付单、回调幂等、订单支付状态联动 |
| 发货/收货 | 8 | 发货、物流事件推进、确认收货 |
| 退款 | 9 | 售后申请、审核、退款、退货回补库存 |

**当前进度**：阶段 0–4 已通过验收；阶段 6/7 的 MVP 简化版（从购物车下单、库存锁定、模拟支付、取消释放）已实现并验证，`mvn clean verify` 147 个测试全部通过；阶段 12 的 Vue 3 用户端前端 MVP 已实现并通过 `npm run build` / `npm test`。优惠券、物流、售后未开始。

**推进顺序**：阶段 0–4 已完成 → 6 订单（MVP 简化版）→ 7 模拟支付（MVP 简化版）已完成 → 5 优惠券 / 8 物流 / 9 售后待确认。阶段 10–12 不属于 MVP。

**MVP 完成判据**：

- 上述闭环可在本地 Docker Compose 环境完整走通；
- 库存、优惠券、下单、支付回调、退款具备并发或重复请求测试且通过；
- 每阶段通过功能验收与文档门禁，未提前实现后续阶段。

## 1. 目标与推进原则

- 采用模块化单体，一个 Spring Boot 应用、一个 MySQL 库。
- 严格按依赖顺序推进，每个阶段结束时系统可编译、可启动、可测试。
- 每个阶段有明确交付物和验收标准，未通过验收不进入下一阶段。
- 不提前实现后续阶段模块；业务包在其所属阶段才加入 `com.mallagent.module.*`（单 Maven 模块，不存在子模块聚合）。
- 核心业务设计（数据模型、状态机、事务边界、幂等方案）先出方案，确认后编码。
- 每阶段结束执行相关测试并如实汇报；不自动提交 Git。

## 2. 业务包与阶段映射

工程是单 Maven 模块，下表是包边界（不是 Maven 子模块）：

| 阶段 | 业务包 | 依赖的前置阶段 |
| --- | --- | --- |
| 0 工程基座 | `com.mallagent.common`、`framework`、`bootstrap` | 无 |
| 1 用户与 RBAC | `com.mallagent.module.user` | 0 |
| 2 商品 | `com.mallagent.module.product` | 1 |
| 3 购物车 | `com.mallagent.module.cart` | 2 |
| 4 库存 | `com.mallagent.module.inventory` | 2 |
| 5 优惠券 | `com.mallagent.module.coupon` | 1、2 |
| 6 订单 | `com.mallagent.module.order` | 1、3、4、5 |
| 7 模拟支付 | `com.mallagent.module.payment` | 1、6 |
| 8 物流 | `com.mallagent.module.logistics` | 1、6、7 |
| 9 售后退款 | `com.mallagent.module.aftersale` | 1、7、8 |
| 10 互动 | `com.mallagent.module.interaction` | 1、2、6 |
| 11 收尾加固 | 全部业务包 | 10 |

顺序说明：

- 库存先于订单，是为了先把“锁定、扣减、释放、回滚”的库存原语和并发控制做扎实。
- 优惠券先于订单，是因为订单价格计算依赖优惠券的锁定、核销与释放；先做订单会导致返工。
- 支付、物流、售后都依赖订单状态机，因此放在订单之后。
- 互动依赖用户、商品和已完成的订单，放在最后。

### 2.1 MVP 范围

MVP 为**阶段 0–9**，构成“浏览 → 加购 → 下单 → 支付 → 发货 → 收货 → 退款”的完整交易闭环。

| 分层 | 范围 | 说明 |
| --- | --- | --- |
| MVP | 阶段 0–9 | 基座、用户/RBAC、商品、购物车、库存、优惠券、订单、支付、物流、售后 |
| MVP 后增量 | 阶段 10 | 点赞、收藏、评论，不参与交易链路 |
| 交付加固 | 阶段 11 | 回归、并发验证、部署与运维文档，不新增业务功能 |
| 已实现（MVP） | 阶段 12 | Vue 3 用户端前端 `frontend/`；管理后台页面未实现 |

说明：

- 优惠券（阶段 5）保留在 MVP 内。订单价格构成依赖优惠券的锁定与核销，先做订单、后补优惠券会导致订单核心链路二次改造，对学习项目是负收益。
- 阶段 10 的任何表、接口、权限码都不得在 MVP 期间创建，包括“先建表占位”。
- MVP 期间的每个阶段仍须通过功能验收与文档门禁，未通过不进入下一阶段。

## 4. 各阶段交付成果与验收标准

### 阶段 0：工程基座

> 历史说明：阶段 0 初始采用 Maven 多模块；阶段 4 步骤 7 前工程已合并为单 Maven 模块，以下多模块名称仅代表当时的交付形态，当前结构以第 2 节为准。

**目标**：建立可运行、可测试、可扩展的工程骨架，不实现任何业务。

**交付成果**

1. 根 `pom.xml`（`mallagent-parent`）：Java 21、Spring Boot 3、依赖版本管理、编译与测试插件。
2. `mallagent-common`：统一响应 `Result<T>`、分页 `PageResult<T>`、`ErrorCode`、`BusinessException`、基础常量与工具。
3. `mallagent-framework`：
   - 全局异常处理、参数校验错误统一转换；
   - 请求 traceId 过滤器；
   - MyBatis-Plus 配置（分页、乐观锁、逻辑删除）；
   - Redis 配置与序列化；
   - RabbitMQ 连接、序列化、基础确认配置；
   - Spring Security 基础配置（先放行健康检查和 OpenAPI，业务白名单在阶段 1 完善）；
   - Springdoc OpenAPI 配置；
   - Flyway 配置。
4. `mallagent-bootstrap`：启动类、`application.yml`、`local`/`test` profile、环境变量占位。
5. `docker-compose.yml`：MySQL 8、Redis、RabbitMQ（含管理台），持久化卷、健康检查、端口映射；提供 `.env.example`。
6. Flyway 基线迁移 `V1__baseline.sql`（可为空结构，业务表从阶段 1 开始）。
7. 健康检查接口 `GET /api/v1/system/health`。
8. 单元测试与集成测试基础设施（测试 profile、测试数据库配置）。
9. 更新 `README.md` 与必要的运行说明。

**验收标准**

- [ ] `mvn clean verify` 实际执行通过。
- [ ] `docker compose up -d` 后 MySQL、Redis、RabbitMQ 均健康。
- [ ] 应用启动成功，能连接 MySQL、Redis、RabbitMQ。
- [ ] Flyway 自动执行，`flyway_schema_history` 中记录 `V1`。
- [ ] 健康检查返回统一响应体，HTTP 200。
- [ ] Springdoc UI 可访问（`/swagger-ui/index.html`），OpenAPI JSON 可获取。
- [ ] 参数校验失败、业务异常、未知异常均返回统一错误结构；响应包含 traceId。
- [ ] 不存在用户、商品、订单等业务表，也不存在任何业务模块。
- [ ] 测试结果如实汇报，包含命令和输出摘要。

**本阶段不做**

- 不创建 `module-*` 业务模块。
- 不实现注册登录、RBAC、商品、库存、订单等任何业务。
- 不接入 Python AI Agent、Vue 前端。

### 阶段 1：用户、RBAC 与认证

**目标**：建立用户体系和权限体系，为后续所有管理端接口提供安全基础。

**交付成果**

1. 数据库表与 Flyway 迁移：`sys_user`、`sys_role`、`sys_permission`、`sys_user_role`、`sys_role_permission`、`user_address`。
2. 初始化数据：初始管理员、内置角色（超级管理员、运营）、权限项；管理员密码不得以明文写入迁移脚本，通过环境变量或启动初始化创建。
3. 用户端接口：
   - 注册、登录、刷新令牌、登出；
   - 当前用户信息查询与修改；
   - 收货地址增删改查、默认地址设置。
4. 管理端接口：
   - 用户分页查询、详情、启用/禁用、重置密码；
   - 角色增删改查；
   - 权限查询与权限树；
   - 用户分配角色、角色分配权限。
5. 安全链路：
   - JWT 签发与校验过滤器；
   - BCrypt 密码编码；
   - 方法级权限控制；
   - 401/403 统一响应；
   - 登出黑名单（Redis）；
   - 登录失败次数限制（Redis，基础版）。
6. 参数校验、唯一性约束、敏感字段脱敏。
7. OpenAPI 文档与测试。

**验收标准**

- [ ] 注册、登录、刷新、登出链路可用；Access Token 过期后返回 401。
- [ ] 密码以 BCrypt 存储，任何接口和日志不回传密码。
- [ ] 未登录访问受保护接口返回 401；无权限返回 403。
- [ ] 管理员可完成角色、权限、用户角色分配；普通用户无法访问管理端。
- [ ] 用户名、手机号等业务唯一键由数据库唯一索引保证。
- [ ] 收货地址只能操作自己的数据，越权访问被拒绝。
- [ ] 登出后旧 Token 失效（黑名单生效）。
- [ ] Flyway 可在空库从 `V1` 执行到阶段 1 最新版本。
- [ ] 认证、权限、越权、并发注册等测试实际通过。

**目标**：建立商品主数据模型和前台查询能力。

- [ ] 管理端接口权限正确。
- [ ] 商品相关测试实际通过。

### 阶段 3：购物车

**状态**：已通过验收（2026-10-31）。详细设计见 `docs/modules/cart.md`。

**目标**：实现购物车增删改查、选中与金额汇总。

- [ ] 并发加入不会产生重复记录。
- [ ] 用户只能访问自己的购物车。
- [ ] 购物车测试实际通过。

### 阶段 4：库存

**状态**：已通过技术验收（2026-11-02）。详细设计见 [`modules/inventory.md`](modules/inventory.md)。

**目标**：提供可靠的库存锁定、扣减、释放、回滚能力，供订单和售后调用。

**交付成果**

1. 表：
   - `stock_sku`：SKU ID、可售库存、锁定库存、版本号；
   - `stock_flow`：业务类型、业务单号、SKU ID、数量、变更前后值、唯一幂等键。
2. 库存操作（通过 `api` 包暴露）：
   - 下单锁定；
   - 支付确认扣减；
   - 取消/超时释放；
   - 售后退货回补；
   - 批量库存快照查询；
   - 管理端手工调整。
3. 并发控制：条件更新 `available >= quantity`，影响行数校验，禁止负库存。
4. 幂等：`(biz_type, biz_no, sku_id)` 唯一约束，重复请求不重复变更。
5. 管理端库存查询、流水查询、调整。
6. 并发测试与幂等测试。

**验收标准**

- [x] 并发扣减同一 SKU 不会出现负库存或超卖。
- [x] 相同业务单号重复锁定/释放/扣减只生效一次。
- [x] 库存流水与库存余额可对账，流水不可重复。
- [x] 释放和回补金额、数量准确。
- [x] 管理端调整有操作记录。
- [x] 并发与幂等测试实际通过。

**实际实现（2026-11-02）**

- 表：`stock_sku`、`stock_flow`，仅两张库存业务表；Flyway V10/V11。
- `InventoryStockApi` 五个方法全部实现：`lock`、`deduct`、`release`、`restore`、`findStocks`，无占位。
- `lock` / `deduct` / `release` / `restore` 通过 `ORDER_LOCK` 行锁串行化订单生命周期；`restore` 仅支持整单回补并限制跨售后累计。
- `findStocks` 单次批量查询，保持首次出现顺序，未初始化返回 `initialized=false`，无副作用。
- 管理端 4 个接口：库存分页、库存详情、调整、流水分页；SUPER_ADMIN 全部权限，OPERATOR 只读。
- 测试：库存相关 71 个测试；全量 131 个测试通过。
- 验证：已有库、空库 `mallagent_inventory_verify_s9` 均通过；V9 → V11 升级验证通过。

### 阶段 5：优惠券

**目标**：实现优惠券模板、领取、下单锁定/核销、取消释放。

**交付成果**

1. 表：`coupon_template`、`coupon_user`（用户券）、必要的领取记录/流水。
2. 券模板：固定金额/折扣类型、使用门槛、适用范围（全场/分类/商品）、有效期、发行总量、每人限领。
3. 领取接口：库存扣减、每人限领、幂等。
4. 用户券列表：未使用、已使用、已过期；可用券查询。
5. 优惠计算接口：供订单预览和下单调用，返回可优惠金额。
6. 状态流转：`UNUSED -> LOCKED -> USED`，取消订单 `LOCKED -> UNUSED`；过期处理。
7. 管理端券模板 CRUD、发放/停用。

**验收标准**

- [ ] 发行量不会被超领；并发领取测试通过。

## 5. 事务、幂等、并发控制清单

### 5.1 总体规则

- 只使用本地事务，不引入分布式事务。
- 事务内不发送 MQ、不调用外部 HTTP、不做长耗时操作。
- 需要异步通知的事件在事务提交后发送；关键事件使用本地消息表或等价机制保证不丢。
- 幂等依赖数据库唯一约束 + 状态条件更新，Redis 仅辅助。
- 并发扣减使用条件更新，禁止 check-then-act。
- 状态机流转使用 `WHERE status = 旧状态`，检查影响行数。
- 默认隔离级别 `READ_COMMITTED`；死锁有限重试。

### 5.2 场景矩阵

| 业务场景 | 事务边界 | 幂等方案 | 并发/一致性方案 |
| --- | --- | --- | --- |
| 用户注册 | 本地事务：用户 + 默认角色 | 用户名/手机号唯一索引 | 唯一约束兜底；冲突返回明确错误 |
| 用户分配角色 | 本地事务：删除旧关联 + 插入新关联 | `(user_id, role_id)` 唯一索引 | 同一用户操作加乐观锁或串行化校验 |
| 角色分配权限 | 本地事务 | `(role_id, permission_id)` 唯一索引 | 同上 |
| 商品 SPU/SKU 保存 | 本地事务：SPU + SKU + 规格关联 | SKU 编码唯一索引 | `version` 乐观锁；规格组合唯一 |
| 购物车加入/修改 | 单表操作，无需跨表事务 | `(user_id, sku_id)` 唯一索引 + 原子 upsert | 数量条件更新；并发合并 |
| 优惠券领取 | 本地事务：用户券 + 模板发放数 | `(user_id, coupon_id)` 唯一索引 + 请求号 | `issued < total` 条件更新；限领校验 |
| 下单 | 本地事务：订单 + 订单项 + 库存锁定 + 优惠券锁定 + 购物车清理 | `Idempotency-Key` / 下单 Token 唯一索引 | 库存条件更新；优惠券状态 CAS；订单状态 CAS |
| 取消订单 | 本地事务：订单状态 + 库存释放 + 优惠券释放 | 业务单号 + 状态条件更新 | 仅 `PENDING_PAYMENT` 可取消；重复取消影响行数为 0 |
| 超时关闭订单 | 本地事务：状态 + 库存释放 + 优惠券释放 | 消息 `eventId` / 订单号幂等 | 状态 CAS；释放操作按业务键幂等 |
| 支付回调 | 本地事务：支付单 + 订单状态 | 外部流水号唯一索引 | 金额校验；支付单/订单状态 CAS |
| 退款执行 | 本地事务：售后单 + 退款单 + 订单售后状态 | 售后请求号唯一 + 退款单号唯一 | 退款状态 CAS；可退金额校验；回补库存幂等 |
| 发货 | 本地事务：发货单 + 订单状态 | 订单号唯一发货 | 仅 `PAID` 可发货；状态 CAS |
| 物流事件更新 | 本地事务：事件 + 发货单状态 | 物流事件 ID 唯一 | 事件乱序时按状态推进规则处理 |
| 点赞/收藏 | 单表操作 | `(user_id, target_type, target_id)` 唯一索引 | 并发插入冲突视为已点赞；计数原子增减 |
| 评论发表 | 本地事务：评论 + 商品评论数 | 订单项维度唯一（如一笔订单项一条评论） | 计数原子更新；资格校验 |
| MQ 消费 | 消费业务本地事务 | 消息 `eventId` 去重表/唯一索引 | 手动 ACK；失败重试；超限进死信 |
| 缓存更新 | 无事务 | 不需要 | 先提交数据库，再删除缓存；TTL 兜底 |

### 5.3 明确禁止

- 禁止“先查询库存再更新库存”。
- 禁止在事务提交前发送 MQ 或调用外部接口。
- 禁止用 Redis 锁替代数据库唯一约束。
- 禁止依赖 RabbitMQ 消息顺序实现业务正确性。
- 禁止跨模块直接修改对方表。
- 禁止为了省事把多个不相关业务塞进同一个大事务。
- 禁止未确认就引入分布式事务、Seata 等组件。

## 8. 设计决策

### 8.1 已确认

| 事项 | 决策 |
| --- | --- |
| Lombok | 引入 Lombok，仅用于实体/DTO 减少样板代码；DTO 仍优先考虑 record |
| 主键策略 | `BIGINT AUTO_INCREMENT` 自增主键，MyBatis-Plus 使用 `IdType.AUTO`；业务单号独立生成 |
| 集成测试 | 使用 Docker Compose 提供的 MySQL、Redis、RabbitMQ，测试库与开发库隔离；暂不引入 Testcontainers |
| JWT 有效期 | Access Token 30 分钟，Refresh Token 7 天，刷新轮换，登出写入 Redis 黑名单 |
| 金额表示 | `BigDecimal` + `DECIMAL(18,2)`，禁止浮点数 |
| 商品分类 | 最多 3 级 |
| 规格模型 | 规格、规格值、SKU 规格关联表，不用 JSON 存核心关系 |
| SKU 组合 | 生成 `spec_signature`，数据库唯一约束 `(spu_id, spec_signature)` |
| 商品搜索 | 第一版使用 MySQL `LIKE`，不引入 Elasticsearch |
| 商品权限 | 统一 `product:*` 命名空间，细分到具体操作 |
| 商品状态 | `DRAFT` / `ON_SHELF` / `OFF_SHELF` 三态，严格校验合法流转 |
| 商品图片 | 数据库只保存 URL，不实现文件上传 |
| 商品删除 | 优先逻辑删除；删除与下架是不同语义 |
| 商品分页 | 最大 `pageSize = 100` |
| 库存并发锚点 | 按 `sku_id` 升序锁定原订单全部 `ORDER_LOCK` 流水行，作为订单生命周期的统一互斥点 |
| 库存幂等 | `UNIQUE(biz_type, biz_no, sku_id)`；普通 `INSERT` 只捕获 `DuplicateKeyException`，再严格比较已有流水 |
| 库存缓存 | MySQL 为唯一事实来源，库存余额和流水不使用 Redis |
| 售后回补 | 阶段 4 仅整单回补；同一售后单幂等，不同售后单累计不超过原扣减数量 |
| findStocks | 单次批量查询、保持首次出现顺序、未初始化返回 `initialized=false`，无写操作 |
| 订单幂等 | 订单先插入占位行，`UNIQUE(user_id, idempotency_key)` 作为并发锚点；重复 key 返回同一订单 |
| 订单库存事务 | 订单、明细、`InventoryStockApi.lock`、购物车清理在同一本地事务内完成 |
| 订单取消 | 仅 `PENDING_PAYMENT` 可取消，调用 `InventoryStockApi.release`；已支付返回冲突 |
| 模拟支付 | 订单行锁 + `InventoryStockApi.deduct` + 支付单 + 状态更新同一事务；重复支付幂等 |
| 购物车存储 | MySQL `cart_item` 为唯一事实来源；购物车状态直接查 MySQL，不使用 Redis 缓存 |
| 购物车幂等 | 添加接口强制 `Idempotency-Key`，MySQL 唯一索引 + 同一事务保证幂等 |
| 购物车删除 | 条目为高频临时数据，使用物理删除 |

### 10.4 遗留技术债与风险

1. 修复前已上架的不完整 SKU 不会被自动回溯修复；其他已有环境上线前应执行一次规格完整性审计。
2. V9 生成列与唯一索引变更会触发表重建，大表环境需要维护窗口。
3. 购物车状态直接查询 MySQL；流量增长后如需缓存，必须重新设计一致性方案。
4. 购物车种类上限 100 仍为应用层软上限，极端并发可能短暂超出。
5. 幂等记录暂无清理任务，后续可增加定时清理。
6. 验证库 `mallagent_final_verify`、`mallagent_cart_verify`、`mallagent_inventory_verify_s8`、`mallagent_inventory_verify_s9`、`mallagent_upgrade_s9` 与本地 Docker 容器仍在，可按需清理；本轮未删除。
7. `findStocks` 对超大 SKU 集合尚未分批，可能生成较长 `IN` 列表。
8. 库存 INT 溢出使用通用业务冲突错误码 `14004`，没有独立错误码。
9. 当前仅支持整单售后回补，不支持部分退款/部分退货；后续扩展需要重新设计累计与售后明细。
10. 库存 API 内部不做局部死锁重试；调用方必须负责事务边界和有限重试。
11. 库存流水尚无归档清理策略，长期运行需要归档方案。
12. 测试库中有 4 个夹具 SKU 因测试直接 SQL 修改库存，导致余额与流水汇总不一致；属于测试构造行为，不是生产代码路径。
13. 后续订单模块必须负责 SKU 可购买校验、整体事务编排和有限重试，库存模块不承担这些职责。
14. 订单不实现超时自动关闭，待支付订单不会自动释放库存。
15. 模拟支付只实现“支付成功”，不实现回调验签、支付单预创建、退款和对账。
16. 未实现优惠券、运费、发票、物流、售后和管理端订单。
17. 订单详情/列表只按用户隔离，无管理端查询。
18. 订单幂等冲突后使用独立 `REQUIRES_NEW` 只读查询读取已提交订单；该事务只读、不写业务数据。
