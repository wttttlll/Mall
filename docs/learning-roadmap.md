# MallAgent 学习路线

> 适用阶段：阶段 0–11（MVP 为 0–9）。
> 与 [`development-plan.md`](development-plan.md) 的分工：后者回答“做什么”，本文回答“该学到什么、怎么自测”。

## 1. 使用方式

- 开工前读对应阶段的“学习目标”，明确这一阶段要建立哪几条主线的能力。
- 收工时用“自测问题”检查自己：**能不看代码讲清楚**才算掌握，答不上来就补，不要靠继续写代码掩盖。
- 每阶段结束后在本文对应行补充“实际收获”，把踩过的坑沉淀成自己的知识。

## 2. 六条技术主线

阶段是按业务横向切的，学习应按技术纵向加厚。同一主线会在多个阶段反复出现，每次加深一层。

| 主线 | 涉及阶段 | 要建立的能力 | 核心问题 |
| --- | --- | --- | --- |
| A 工程与架构 | 0、11 | 单 Maven 模块内的包边界、依赖方向、配置分层、构建与测试闭环 | 包边界按什么切？依赖方向为什么不能反向？ |
| B 安全与权限 | 1、11 | 无状态认证、RBAC、越权防护、敏感信息处理 | 无状态认证怎么登出？越权发生在哪一层？ |
| C 数据建模 | 2、3、4、5、6 | 关系建模、唯一约束承载业务规则、索引设计 | 什么时候用关联表、什么时候能冗余？唯一索引如何兜住并发？ |
| D 事务与并发 | 4、5、6、7、9 | 事务边界、条件更新、幂等、状态机 CAS | 为什么禁止 check-then-act？影响行数为 0 意味着什么？ |
| E 缓存与消息 | 2、6、7、8 | Cache-Aside、失效策略、消息幂等与重试 | 缓存与库不一致的窗口在哪？消息为什么不能替代方法调用？ |
| F 交付与运维 | 0、11 | Flyway 迁移、环境变量、可观测性、故障排查 | 迁移为什么不可修改？一个请求出问题怎么定位？ |

## 3. 阶段学习内容与自测问题

### 阶段 0：工程基座

**学习目标**：理解模块化单体的依赖约束；掌握 Spring Boot 自动配置与配置分层；跑通 Flyway、健康检查、统一响应体。

**自测问题**

1. 为什么 `com.mallagent.common` 尽量不依赖 Spring？
2. `com.mallagent.framework` 为什么不能依赖业务包？
3. 统一响应体里的 `traceId` 从哪里来？没有它排障会缺什么？
4. Flyway 的版本号一旦执行，为什么不能再改？

### 阶段 1：用户、RBAC 与认证

**学习目标**：掌握 Spring Security 过滤链、JWT 签发校验、BCrypt、方法级鉴权；理解无状态认证的代价。

**自测问题**

1. Access Token 与 Refresh Token 各自的职责和有效期取舍是什么？
2. JWT 是无状态的，登出为什么还要 Redis 黑名单？黑名单为什么不能是唯一防线？
3. 401 和 403 的边界在哪里？混用会造成什么安全问题？
4. 用户只能访问自己的收货地址——这个约束应该在 Controller、Service 还是 SQL 层保证？
5. 为什么唯一性必须由数据库唯一索引保证，而不是先查后插？

### 阶段 2：商品

**学习目标**：掌握聚合建模（SPU/SKU/规格）、状态机、可见性规则、缓存读写策略。

**自测问题**

1. SPU 与 SKU 各自承载什么信息？为什么价格挂在 SKU 上？
2. 规格为什么用关联表而不是 JSON 字段？两种方案各有什么代价？
3. 商品状态机有哪些合法流转？为什么用条件更新而不是先读后写？
4. 用户端“只看到上架商品”这条规则，在列表和详情两处如何保证一致？
5. 缓存删除失败会发生什么？TTL 在这里起什么作用？
6. 为什么商品搜索先用 `LIKE` 而不是引入 Elasticsearch？

### 阶段 3：购物车

**学习目标**：掌握幂等写入、并发合并、服务端计算金额。

**自测问题**

1. `(user_id, sku_id)` 唯一索引如何避免并发重复插入？冲突后应该更新还是报错？
2. 为什么客户端传来的金额一律不可信？
3. 购物车为什么以 MySQL 为准而不是 Redis？
4. 幂等键为什么必须与购物车写入在同一事务内？只靠先查后写会出什么问题？
5. 缓存 TTL 为什么只影响性能、不影响数据正确性？

**实际收获**

- 用 `UNIQUE (user_id, sku_id)` + `INSERT ... ON DUPLICATE KEY UPDATE` 实现原子合并，避免 check-then-act。
- 幂等表用 `(user_id, idempotency_key)` 唯一索引兜底，`claim_token` 区分“本次新插入”和“重复请求”。
- 幂等记录与购物车写入放在同一事务；超限回滚时幂等记录一并回滚，允许客户端重试。
- 并发写幂等表可能死锁，采用最多 3 次有限重试并记录日志。
- 购物车状态直接查询 MySQL，不做 Redis 缓存；商品价格每次从商品模块读取。
- 缓存删除失败和并发回填的竞态难以在短 TTL 下彻底消除，因此本阶段优先保证正确性，暂不缓存购物车。

### 阶段 4：库存

**学习目标**：掌握条件更新、影响行数校验、库存流水与对账、幂等键设计。

**自测问题**

1. `UPDATE ... WHERE available >= ?` 为什么能防超卖？影响行数为 0 时业务上意味着什么？
2. 库存流水为什么需要 `(biz_type, biz_no, sku_id)` 唯一约束？
3. 锁定、扣减、释放、回补四种操作分别在什么时点发生？
4. 如果库存放 Redis 扣减，会引入哪些一致性问题？

**实际收获**

- 用 `UPDATE ... WHERE available_stock >= ?` 条件更新和影响行数判断防超卖；影响行数为 0 代表库存不足、记录不存在或溢出，需要结合场景区分。
- `ORDER_LOCK` 流水同时是订单生命周期的互斥锚点：`SELECT ... FOR UPDATE` 锁定订单全部锁定行，再处理 deduct/release/restore，避免只根据 `stock_sku` 余额判断订单状态。
- 库存流水占位与库存更新在同一事务内；更新后持有库存行锁读取真实后值回填 before/after，已提交流水不允许空值。
- 业务唯一键 `(biz_type, biz_no, sku_id)` 是幂等最终防线；普通 `INSERT` 只捕获 `DuplicateKeyException`，再严格比较已有流水，不能吞掉其他 SQL 错误。
- 多 SKU 统一按 `skuId` 升序更新，避免不同订单反向加锁死锁；库存 API 内部不做局部重试，由调用方决定事务边界和有限重试。
- 售后退补只支持整单，累计回补按 `ref_biz_no + sku_id` 汇总已完成流水，避免不同售后单重复回补。
- `findStocks` 使用单次批量 `IN` 查询并保持首次出现顺序；未初始化 SKU 返回 `initialized=false`，查询本身不产生任何写操作。

### 阶段 5：优惠券

**学习目标**：掌握发行量控制、用户券状态流转、优惠金额计算、释放幂等。

**自测问题**

1. 券的“锁定”和库存的“锁定”本质区别是什么？
2. 如何保证不超发、同一用户不重复领取？
3. `UNUSED → LOCKED → USED` 与取消后的 `LOCKED → UNUSED`，各自用什么条件更新？
4. 满减、折扣、门槛、适用范围叠加时，金额计算顺序如何影响最终结果？

### 阶段 6：订单

**学习目标**：掌握事务边界划分、订单状态机、下单幂等、超时关闭方案。

**自测问题**

1. 一笔下单事务包含哪些写操作？为什么它们必须在同一事务内？
2. 为什么事务内不能发 MQ？提交后发送如何保证不丢？
3. `Idempotency-Key` 与数据库唯一约束是什么关系？
4. 用户取消和系统超时关闭有什么区别？重复执行是否安全？
5. 订单号为什么不复用主键？

### 阶段 7：模拟支付

**学习目标**：掌握回调幂等、金额校验、支付与订单状态联动。

**自测问题**

1. 重复回调为什么不能靠“先查状态再更新”解决？
2. 回调金额与订单应付不一致时为什么必须拒绝？
3. 支付成功后为什么要发事件，而不是直接改订单表？

**阶段 6/7 实际收获（MVP 简化版）**

- 下单幂等用订单占位行 + `UNIQUE(user_id, idempotency_key)` 实现：先占用幂等键，再锁购物车、计价、锁库存；失败时占位行与库存、购物车一起回滚。
- 并发相同幂等键会在唯一索引上等待；冲突后用独立 `READ_COMMITTED` 只读事务读取已提交订单，避免当前事务快照看不到新订单或行锁互相死锁。
- 并发不同幂等键通过购物车 `SELECT ... FOR UPDATE` 串行化，保证同一批已勾选条目只能生成一笔订单。
- 支付和取消都用订单行 `SELECT ... FOR UPDATE`；状态用条件更新，支付与取消并发时恰好一个成功。
- 重复支付在订单行锁下看到 `PAID` 后直接返回已有支付单，不重复调用库存 `deduct`。
- 订单金额只在服务端根据商品当前价格计算；购物车、商品、地址、库存均通过现有 `api` 契约复用。

### 阶段 8：物流

**学习目标**：掌握事件幂等、乱序处理、状态推进规则。

**自测问题**

1. 物流事件重复推送如何幂等？
2. 事件乱序到达时，靠什么保证最终状态正确？
3. 发货的前置状态约束写在哪一层？

### 阶段 9：售后退款

**学习目标**：掌握可退金额计算、重复退款防护、退款与库存回补的联动。

**自测问题**

1. 可退金额怎么算才不会超退？并发退款时靠什么兜底？
2. 仅退款与退货退款对库存的影响有何不同？
3. 退款单号、售后请求号、外部流水号分别在防什么重复？

### 阶段 10（MVP 后）：互动

**学习目标**：掌握计数一致性、唯一约束去重、评论资格校验。

**自测问题**

1. 点赞计数为什么不能用“先查数量再 +1”？
2. 重复点赞应该报错还是幂等成功？两种选择的业务含义是什么？

### 阶段 11：收尾加固

**学习目标**：全链路回归、并发验证、索引审查、交付文档。

**自测问题**

1. 如何用测试证明“不会超卖”？
2. 慢查询怎么定位？索引该按什么顺序设计？
3. 缓存失效、消息重复、消费失败这几种异常，系统当前如何应对？

## 5. 常见误区

- **用代码量衡量进度**：阶段推进的标志是能讲清设计，不是模块数量。
- **过早抽象**：为“以后可能用到”预留接口，会让当前设计变复杂，且大概率预留错。
- **把幂等交给 Redis**：Redis 只能辅助，唯一约束才是最后防线。
- **先查后改**：任何“读状态 → 判断 → 写状态”的写法，在并发下都可能出错。
- **文档后补**：阶段结束不写，后面补的成本是翻倍，且容易写成与代码不符的假文档。
